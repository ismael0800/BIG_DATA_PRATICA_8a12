1. Por que um orquestrador existe?

Você já viu um pipeline: primeiro ingere dados, depois transforma (dbt, Spark ou Python), em seguida valida e, por fim, libera um relatório. O desafio não é somente escrever cada script. É garantir que cada parte comece na hora certa.

Ingestão→Transformação→Validação→Relatório

Cron: despertador

O cron chama um comando num horário: por exemplo, “rodar às 3h”. Não coordena por si só as dependências de um pipeline complexo. Pode receber verificações externas/scripts, mas isso precisa ser construído.

Airflow: maestro

Airflow organiza as dependências, dispara execuções, guarda logs, acompanha falhas, oferece tentativas (retries) e painel de monitoramento. Não é banco de dados e não substitui o trabalho do dbt.

Situação real

Um relatório começa às 03:00, mas a extração de pedidos atrasou e só termina às 03:07. Se o relatório ler a fonte antes da extração, ele pode mostrar números incompletos. O orquestrador faz a transformação esperar a extração estar pronta.

2. DAG e dependências: o mapa da execução

DAG quer dizer Directed Acyclic Graph: grafo direcionado (as setas indicam a ordem) e acíclico (não pode haver loop). Cada bloco é uma task. Se A depende de B e B de A, ninguém consegue começar.

extrair→aguardar_arquivo→transformar→validar→notificar

O símbolo >> expressa dependência no código: extrair >> transformar significa que transformar espera extrair. Em um fluxo paralelo, duas transformações podem partir após a mesma extração, e uma etapa final espera ambas.

extrair >> [limpar_clientes, limpar_pedidos]
[limpar_clientes, limpar_pedidos] >> validar
Airflow e dbt têm DAGs, mas com papéis diferentes: dbt encadeia modelos SQL; Airflow encadeia tarefas e sistemas (extrair arquivo, esperar, dbt, validar e avisar).
16–22 min · Guia de conceitos

3. Operator, TaskFlow, sensores, horário e falhas

Task e Operator

Uma task é uma unidade de trabalho. Um Operator descreve o tipo de trabalho (BashOperator para comando, PythonOperator para função). A TaskFlow API usa @task e @dag para criar tarefas a partir de funções Python.

Sensor

Espera uma condição, como a chegada de um arquivo. poke verifica ocupando o worker enquanto espera. reschedule libera o slot entre verificações.

schedule e catchup

schedule="0 3 * * *": diário às 3h (no fuso configurado). catchup=False: não tentar automaticamente recuperar cada período antigo desde o início.

Retries e logs

retries=2 permite três tentativas totais. Os logs registram erro e tentativas. O Airflow real respeita retry_delay; o simulador local acelera para a aula.

from airflow.sdk import dag, task  # API pública Airflow 3

@dag(schedule="0 3 * * *", catchup=False, ...)
def meu_fluxo():
    @task
    def extrair():
        return {"arquivo": "pedidos.csv"}
    @task
    def transformar(dados):
        print(dados["arquivo"])
    transformar(extrair())

meu_fluxo()

Status importantes: queued (na fila), running (executando), success (concluído), failed (falhou), upstream_failed (bloqueado por falha anterior). Nosso laboratório usa também waiting como marcador **didático** de sensor aguardando.

6. Falha controlada e tentativas (retry)

Agora vamos provocar uma falha de propósito na tarefa de validação. O objetivo não é quebrar a instalação: é observar o que o orquestrador faz quando algo dá errado. Aqui, o executor didático repete imediatamente a validação, para caber no tempo da aula. O Airflow real normalmente respeita a pausa configurada.

python executar_local.py --cenario falha

Resultado esperado: aparecem 3 linhas com ERRO validar_qualidade (tentativa 1/3, 2/3 e 3/3), linhas de RETRY, depois ESTADO FINAL: FAILED e notificar_sucesso:upstream_failed. O terminal pode exibir código de saída 2: isso é esperado, porque a falha é o experimento.

Por que bloquear a notificação?

Porque não é correto avisar “relatório aprovado” se o teste de qualidade falhou. O estado upstream_failed representa que não foi possível iniciar uma tarefa seguinte devido ao problema anterior. Em Airflow real, estados downstream também dependem das trigger rules.

Evidência 2: Falha e 2 retries

Print mostrando tentativa 1/3, 2/3, 3/3, FAILED e upstream_failed.

7. Sensor aguardando e liberando o fluxo

Às vezes a extração acabou, mas uma confirmação externa ainda não chegou. O sensor impede o processamento seguinte até essa condição ser atendida. Vamos simular a chegada da confirmação saida/sinal.ok em dois momentos:

Passo A: primeiro rode sem criar o sinal:

python executar_local.py --cenario sensor

Resultado esperado antes: aguardar_arquivo:waiting, as etapas posteriores ficam blocked e o estado final é WAITING. Se já existir saida/sinal.ok de outra execução, apague somente esse arquivo e repita o passo A.

Passo B: crie a confirmação e execute novamente:

python criar_sinal.py
python executar_local.py --cenario sensor

Resultado esperado depois: ESTADO FINAL: SUCCESS com todas as tarefas aprovadas. Isso não é uma espera contínua no Airflow real: o executor local representa a espera como um estado e deve ser executado novamente após o sinal.

Evidência 3: Sensor antes e depois
